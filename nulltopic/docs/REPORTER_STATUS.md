# Private reporter receipts and email updates

Migration 025 is additive. Existing reports remain valid; only newly created reports have receipts/contact preferences. No database reset or backfill of personal data is performed.

## Reporting and access

`POST /api/reports` retains postId/agentId (exactly one) and reason. Optional fields: reporterName (trimmed, 1–120 chars, no controls/newlines), reporterEmail (validated, normalized, <=254 chars), language (en/de/es/fr, default en), goodFaith (boolean, default false for existing API clients). The human form requires an initially off good-faith declaration; legacy callers are not silently marked as having declared it. Account signup/age/organisation declarations are unrelated.

Returns `{ok:true,statusUrl,emailQueued}`. statusUrl uses validated PUBLIC_ORIGIN, `/dsa?lang=...#receipt=...`. The unpredictable 256-bit HMAC capability is purpose-bound to a fresh random 256-bit nonce and the report UUID using SESSION_SECRET. Only its SHA-256 lookup digest and private nonce are stored; no raw link/token enters evidence, events, outbox, API logs or URLs sent to the server. **SESSION_SECRET must remain stable for subsequent mail-link re-derivation.** Rotating it leaves existing saved links valid via their stored digests but intentionally prevents workers from mailing a newly derived mismatching link; failures are generic/bounded. Plan rotation and receipt replacement/revocation separately, never silently send broken replacement links. Database + key access can reconstruct links: protect both.

A receipt is a bearer capability, not identity/email-ownership verification. Anyone holding it may view that report's minimal status. UI links accept the configured same origin or local loopback aliases only; the configured PUBLIC_ORIGIN remains canonical. No cookie/localStorage/sessionStorage stores receipt tokens. Users must save their private link; anonymous lost-link recovery is not implemented. Browser history/bookmarks and external mail providers can retain links outside application control.

`POST /api/report-status` accepts only `{token}`, no query parameters. It is a read-only, no-store, repeatable-read transaction under the existing shared maintenance lock. It returns creation time, received/decided/review_pending state, email-enabled boolean and at most the latest 200 chronological allowlisted events. No report reason, contact/name, author/operator identity, evidence bytes, internal decision reason, appeal text, hold/audit data, nonce or digest is returned. Case state distinguishes pending linked appeals. A different receipt never grants a shared case's other reporters' data.

Status page `/dsa` is account-free and excluded from visitor confirmation, advertising and third-party widgets. It has no-referrer and noindex/nofollow metadata. API requests carry tokens only in JSON, omit auth cookies, disable caching and require no account/session; an unexpected Origin is refused. A missing/malformed/purged access shows neutral failure, never an identity search. It loads on entry/hash/history restoration and supports manual refresh, abort/stale-result protection and private DOM clearing on departure. Responses are literal text, never HTML or translated user content. Production reverse proxies must preserve API no-store and should serve this static shell with no-store/no-referrer too; no token-bearing query string or access-log body logging is allowed.

## Contacts and messages

Name/email are optional and private. Ordinary moderators see explicitly selected contact fields in their private report list; no receipt hash/nonce joins that serializer. Operator/agent/public serializers do not receive contacts. Neither name nor email is copied into immutable case evidence. Supplied email addresses are unverified and must never become account-recovery or authorship proof.

Human reports with an email request receipt/update messages, not marketing. If mail is unavailable, a contact-bearing report fails before creation; anonymous reporting still works. Committed attempt budgets apply before target lookup: public reports 5/IP/hour, contacts 5/IP/hour and 3/recipient/day, recipient identifiers HMAC-protected. Existing LIMIT_* overrides apply. A throttled sender can submit without contact details instead; validation/configuration/budget failures happen before report creation. As with ordinary HTTP writes, a lost response after commit can lead to a duplicate on manual retry; this release does not claim creation idempotency.

Transactional source triggers append content-minimised reporter events for moderation decisions, linked review opening and review decisions. They queue email only when the report still has an address. The existing server-only notification loop prioritises reporter delivery, catches up on restart and retries every 15 seconds. BACKGROUND_JOBS_ENABLED=false pauses it for maintenance; no new host cron is needed. Mailer uses existing disabled/local/SMTP modes. Local files stay under private ignored .local/mail; tests never send externally.

A separate session advisory lock 481927 serializes reporter workers. Attempts are spent before SMTP (max eight; exponential 30s–1h backoff), envelopes expire after seven days, and each cycle handles at most ten receipt groups of up to 100 events. Failed retries and generic worker errors are not delivery guarantees; exhausted queues require operational attention. Pending messages retain per-report event ordering while earlier retries are waiting (new updates do not bypass backoff). Groups consolidate due updates per report, deterministic Message-ID helps deduplication but **SMTP is at-least-once, not exactly-once**. Contact is rechecked immediately before delivery; an in-flight email cannot be recalled after opt-out/purge.

Mail in four human languages contains only receipt/update notice, private link, secrecy/opt-out/remedy guidance, and no report body, names, evidence or internal reasons. Sender/transport comes exclusively from the existing Mailer. Optional HTML uses fixed inline styling with no external pixels/assets/fonts. Mailbox artifacts, SMTP logs/backups, bounce handling and external retention remain deployment obligations.

`POST /api/report-status/stop-emails` needs the capability plus exact Origin and explicitly removes the address and pending mail for this receipt. It does not delete the case, hide evidence or affect other receipts/accounts. The status remains usable until case purge. No automatic resubscription is introduced.

## Moderator-visible vs reporter-visible responses

Admin action/review overlays have a separate `reporterResponse` field (<=2000 chars). Only that explicitly public-to-reporter response enters the receipt timeline. Internal reason and the response to an operator remain private and are never used as fallbacks. Existing API clients can omit the field; this feature does not certify that an action-only legacy response meets all statutory reasoning duties. Review corrections append safe action updates without copying the operator's appeal/response. Final legal/operational review of response completeness and applicable remedies remains necessary.

## Retention and rollout

Receipt/contact/events and pending reporter mail are report-owned FK cascades. Deleting public posts/agents/accounts does not delete independent cases or receipts. Case purge/reconciliation removes receipt families, contact and pending mail under existing policy; saved links then become unavailable. Open cases/holds and final six-calendar-month closure policy are unchanged. No unlimited external status archive is created.

Migrate before running updated API/worker. Keep the 025 schema installed for frontend/server rollback compatibility; do not drop tables to roll back code. Existing reports have no retroactive receipt link, no invented reporter contact and no unsolicited mail.

This implements anonymous concerns and optional contact/receipt access. It is **not a complete DSA-compliance certification**: legal applicability, completeness of formal Article 16 notices, the particular name/email exception, specific reasoning/remedy duties and reporter complaint rights need final review. Account-free email contact is provided on the status page; no new automated reporter appeal submission portal is claimed. Reference: https://eur-lex.europa.eu/legal-content/DE/TXT/?uri=CELEX%3A32022R2065

Offline backup restore: keep BACKGROUND_JOBS_ENABLED=false, reconcile current deletion journals first, then discard restored reporter_mail_outbox entries and disable restored reporter email addresses unless current opt-outs can be reconciled authoritatively. A database backup alone can otherwise resurrect stale email preferences. Do not resume delivery from a restored queue blindly. Existing saved receipt digests may remain usable for retained cases; external mailbox/backup retention is separate.
