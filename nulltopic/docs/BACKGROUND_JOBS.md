# Built-in background tasks

The normal backend entrypoint starts a single-flight scheduler after listening. It checks every 30 seconds, runs conversations/auxiliary cleanup daily at **03:15 Europe/Berlin**, and private-case cleanup at **03:30 Europe/Berlin**. No cron dependency, system cron installation or external timer is required. Berlin scheduling uses explicit IANA timezone calculations, including daylight-saving transitions. Only these two fixed jobs are supported: this is not an arbitrary command runner or editable cron-expression interface.

On startup, the most recent elapsed daily slot is compared with the database's last successful slot. Missed work runs once against current eligibility, rather than replaying every missed day. Failures retry after 15 minutes; the retry deadline survives restart. Multiple processes share per-job PostgreSQL session advisory locks (481923 cases, 481924 conversations). Runs are recorded before work; after a crash the next lock holder marks orphaned running records interrupted. The existing case-export/conversation locks remain in place. Shutdown stops new scheduling, stops accepting HTTP requests and awaits in-flight scheduled/manual work before closing the pool. SIGKILL/crashes instead use the interrupted-run recovery path.

`BACKGROUND_JOBS_ENABLED=false` disables scheduling, not explicit CLI/manual actions. Use it during offline restore. Changing the variable requires a backend restart. The scheduler is started only by `src/server.ts`, never by merely creating the Fastify application or importing a module (including tests).

## Admin operations

Ordinary admins see **Background tasks**: last attempt, last successful run, next daily slot, retry time, ready/running/failed/overdue state and the latest 20 runs. Counts represent conversations or cases, not individual descendant messages or technical auxiliary rows. Only successful counts are reported; failed/partial work has unknown count, not a misleading zero. No content, contact data, target UUIDs, stack traces or raw database errors enter history/logging. The database retains completed run history for 35 days; compact last-success scheduling metadata persists. Expired previews are swept on successful work. Root, operators, agents and guests cannot read or operate these tasks.

A manual icon is offered only for failed/overdue work and not while running. Preview returns a complete current eligibility count without deleting anything. It creates an admin-bound single-use preview valid for five minutes. A separate explicit confirmation POST validates role/auth version, CSRF, preview, due state and job lock again. Counts may change; work always rechecks live eligibility, including case holds/open appeals, at execution. A stale preview, another admin's preview, an already-successful slot or a concurrent run is rejected. Failed work requires a fresh preview. Automatic recovery continues without manual interaction.

The visible panel refreshes every 30 seconds, only while active/visible and without an open confirmation. It backs off after failures, clears on workspace/session departure and uses the existing passive session-store mode: GET `/api/admin/jobs` does not renew authenticated idle time. Manual preview/start and deliberate navigation retain their ordinary session semantics.

## Common execution path and operational safety

CLI `cleanup:cases` and `cleanup:conversations` still work, now record real runs in the same history. CLI dry-run stays mutation-free and creates no run history or journal. Explicit CLI work can be forced even when today's scheduled slot already succeeded; the web button cannot. Case CLI/server/manual execution share the identical family purge and atomic private journal exporter. A failed export makes the job fail, even if some batches have already committed; retry exports the retained DB ledger again. Details of the 30-day external backup bound, private 35-day deletion journal and offline restore reconciliation remain in CASE_RETENTION.md.

Do not enable the old external systemd/cron examples alongside the built-in scheduler. If an external scheduler is preferred, set `BACKGROUND_JOBS_ENABLED=false` explicitly and monitor it separately. Migration 017 adds only task metadata. After the development watcher reloaded, both initial catch-up runs succeeded with zero conversations and zero case files deleted. Existing auxiliary expiry housekeeping may run as part of conversation maintenance. Destructive scenario verification uses synthetic workers/isolated test databases only.

Before restoring a server: stop service traffic/scheduling, obtain the latest trusted out-of-band case deletion journal, reconcile it **before** cleanup can overwrite that journal, and only then restart with scheduling enabled. This dashboard is not a backup manager and does not configure external backup expiry or replication.
